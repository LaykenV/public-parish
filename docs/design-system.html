Public Parish design system

Version 0.3. This file records the selected Coss UI component model, semantic colors, typography, logo, interaction rules, and product contracts.

Purpose and authority

Public Parish is a free, open-source, nonpartisan Louisiana civic application. Its interface helps residents discover local-government decisions, inspect the official evidence, ask source-grounded questions, follow an issue, and learn what happened.

This file controls

  • Brand colors and their permitted roles.
  • Logo use and favicon behavior.
  • Mobile, touch, motion, and accessibility rules.
  • Behavioral contracts shared by reusable components.
  • Design patterns that Public Parish will not use.

Defined for Slice 5

  • Decision-card density and evidence-gutter composition.
  • Issue, meeting, Explore, Ask, and account layouts.
  • The complete resident sitemap and responsive shell.
  • Loading, failure, limited, account, and live states.

Page-specific briefs must cite this file and may narrow these rules. They may not weaken them. Start with marketing-page.md for the first landing-page experiment and resident-interface-plan.md for the complete application.

Design principles

Resident before institution

Lead with what may change, where, when, and what the public can still do. Government terminology remains available as supporting context.

Evidence stays beside the claim

Dates, amounts, votes, deadlines, consequences, and outcomes must open the source excerpt that supports them. A source list at the bottom is not enough.

Uncertainty is visible

Missing or delayed evidence produces a limited state, a dated explanation, or no publication. The interface never fills a gap with confident filler.

Louisiana without costume

Color and rhythm may feel local. Avoid tourism graphics, sports branding, campaign language, government seals, and decorative civic clip art.

The prelaunch Louisiana relief is a coverage indicator. Keep it on the hero's page plane with labeled launch pins. Do not frame it as a card or add decorative map furniture.

Color system

Public Parish uses the Coss UI semantic token model. Deep purple marks primary actions, selection and focus. A lavender off-white page surrounds near-white desktop sections and white cards. Mobile cards sit directly on the page to preserve reading width. Dark plum carries headings, softer ink carries body text, and muted text marks metadata. Green and amber appear only for factual success, source health, and warning states. Color never carries a status by itself.

Logo foundation

The selected mark is a path-based double P inside a neutral rounded square. It reads at favicon size, avoids government-seal cues, and keeps the product name as live text.

Use rules

  • Keep the mark legible at 16, 32, 64, and 180 pixels.
  • Use the symbol alone for favicons and compact app chrome.
  • The resident shell uses the mark and live-text name as the Home control on every route, including Home.
  • Use the name as live text beside the mark in compact app contexts.
  • Do not bake the name into a raster logo image.
  • Do not recolor individual letterforms.
  • Do not imply government ownership or endorsement.

The logo is selected for the prelaunch system. Revisit it only when a real legibility or ownership problem appears.

Typography

Inter handles body text, headings, controls, and navigation. Geist Mono handles technical identifiers and owner review data. Resident dates, source labels, and preferences use Inter. These roles match Coss UI's font-variable contract.

Selected roles

  • Inter at 16 CSS pixels or larger for body text.
  • Inter at 600 or 700 for headings and primary labels.
  • Inter for resident metadata. Geist Mono for technical identifiers.
  • Upright emphasis. Do not use italic contrast text.
  • Tabular numerals where dates, money, or vote counts need it.
  • A comfortable text measure near 55 to 72 characters.
  • Long headings must wrap without horizontal overflow.

Type behavior

  • Headings use tight spacing, not decorative type effects.
  • Controls keep Coss UI's compact, medium-weight treatment.
  • Data labels remain short and never replace plain language.
  • Responsive sizes use fluid clamps and must work at 320 pixels.

Layout and spacing

Use a 4-pixel spacing base. Agents may create different compositions, but they must express spacing through named tokens rather than isolated values.

  • Mobile content must work at 320, 375, 414, and 768 pixels.
  • Use minmax(0, 1fr) for shrinkable grid tracks.
  • Set overflow-x: clip on the document, not hidden.
  • Do not force every section into the same centered container.
  • Do not use full-width pill containers as layout decoration.
  • Keep section structure meaningful. Number only real sequences.

Resident pages

The Home palette continues through reading, search, saved preferences and supporting pages. These patterns are implemented locally and await release checks.

Read a story or record

Use a clear title, compact geographic metadata and purple actions. Keep accepted claims intact. Story section links lead to the timeline, next action, unknowns and official evidence.

White source panels separate excerpts from the page. Amber marks missing evidence. Government outcomes use neutral status colors.

Search and manage

Search, Following and Coverage use white cards on the lavender page. Forms have visible borders and 16-pixel input text on phones. Place the coverage request form before its supporting explanation.

Page titles use a shared fluid size between 1.85 and 2.75 rem. Preserve the Home hero's separate scale.

Reading and Ask, September 10

Stories stay above local issues even after area selection. Mobile omits the 3D Louisiana. Issues, decisions and meetings share numbered source controls, plain notices and narrow-screen reading layouts.

Keep conversations above a persistent composer with an up-arrow send button at the lower right. Empty suggestions sit above the composer. Mobile reading pages open Ask in a drawer and retain drafts on close.

Drawers use 420ms cubic-bezier(0.4, 0, 0.6, 1) motion. Phone drawers rise from below; desktop source drawers enter from the right. Reduced motion removes transitions. Keep Close visible and preserve reading position.

Mobile and touch

Phone use is the primary design case. Desktop is the expansion of the mobile experience, not the source layout squeezed smaller.

Touch contract

  • Interactive targets have a 44 by 44 CSS pixel minimum.
  • Primary actions remain on one line at supported widths.
  • No essential action depends on hover.
  • Do not place competing tap targets inside a clickable card.
  • Keep visible focus and a logical keyboard order.

Horizontal rail contract

  • Use rails only for finite peer collections such as decisions.
  • Use native overflow and scroll-snap-type: x mandatory.
  • Show part of the next card so touch users discover the rail.
  • Never hijack vertical page scrolling.
  • Provide keyboard access and desktop previous or next controls.
  • Do not require drag as the only input method.

Vertical space contract

  • The mobile top bar scrolls away with the page.
  • The animated hamburger opens a floating Coss Popover.
  • The mobile header uses a 3.5 rem row with a 44-pixel menu button. Home, Explore, Ask, Following and Coverage remain in the menu.
  • Remove bottom navigation and its reserved space. Close, Escape and outside dismissal remain available with keyboard focus handling.
  • Do not stack a fixed notice, composer, and navigation bar over the same reading window.

Sheet and gesture contract

  • A written control opens every sheet.
  • An open sheet may use a grabber, medium and full heights, and downward dismissal.
  • Keep explicit Close and safe backdrop controls. Return to the exact opener.
  • Safari owns the screen-edge Back gesture.
  • Do not swipe between top-level routes, snap the vertical page, or hide destructive actions behind swipe alone.

Motion

Motion explains state or sequence. It does not decorate every section. The marketing page receives two coordinated moments: one restrained hero treatment and one evidence-sequence animation. 

:root {
  --dur-instant: 100ms;
  --dur-fast: 160ms;
  --dur-standard: 240ms;
  --dur-deliberate: 520ms;
  --ease-out: cubic-bezier(0.16, 1, 0.3, 1);
  --ease-in: cubic-bezier(0.7, 0, 0.84, 0);
  --ease-in-out: cubic-bezier(0.65, 0, 0.35, 1);
}
  • Animate transform and opacity. Do not animate layout properties.
  • Focus rings appear immediately and never animate.
  • No bounce, overshoot, scroll-jacking, or marker pulses.
  • The Louisiana relief may use low-rate lighting while visible. Pointer movement across the hero controls a restrained tilt on devices with hover and a fine pointer. Touch-first devices render one static frame.
  • Motion cannot hide source status or delay access to content.
  • Reduced motion shows the final state immediately or uses a short opacity change.

Accessibility floor

  • Meet WCAG 2.2 AA contrast and interaction requirements.
  • Use semantic landmarks and a single clear heading hierarchy.
  • Support complete keyboard navigation and visible focus.
  • Label every icon and status with accessible text.
  • Announce material realtime changes without stealing focus.
  • Return focus after drawers, dialogs, and citation panels close.
  • Use readable local dates and machine-readable timestamps.
  • Identify the destination of every official-source link.

Patterns to reject

Visual

  • Eyebrow labels used as decoration.
  • Pills used for navigation, headings, or generic metadata.
  • Italic words inserted only to create contrast.
  • Gradient blobs, AI sparkles, fake browser chrome, or phone frames.
  • A repeated hero, three-card grid, CTA, footer template.
  • Equal-weight blue, green, and amber blocks.
  • Red-versus-blue political framing.

Content

  • Invented metrics, testimonials, partner logos, or usage claims.
  • Claims that unsupported regions are covered.
  • Government motives not stated in the official record.
  • Hackathon or sponsor material placed above resident value.
  • Backend jargon in resident-facing headings.
  • Generic claims that could describe any civic application.

How this foundation evolves

  1. Start with Coss UI primitives and semantic tokens for common controls.
  2. Compose civic product patterns from real source and decision data.
  3. Record reusable decisions here after runtime verification.
  4. Keep page-specific WebGPU and motion work outside primitive controls.
  5. Verify each component on real mobile widths and real civic data.

Page-specific code may narrow these rules. It cannot weaken the product evidence, accessibility, mobile, or status contracts.
